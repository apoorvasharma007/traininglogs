Technical Design · App v3.0.0 · 2026-07-26 · github.com/apoorvasharma007/traininglogs

traininglogs

A pipeline for turning workout notes into a queryable, chartable training history.

Why this exists

I lift weights. I write down what I do, and later I want to answer questions: am I getting stronger? am I hammering the same muscle group three days in a row? what was my squat doing six months ago? did the deload actually do anything?

Spreadsheets work until they don't. Off-the-shelf apps assume a workout shape that isn't mine — they don't model myo-reps, partial reps, or the difference between a warmup set and a working set the way I think about them. The shape I want is: write the session the way I'd write it in a notebook, and have a system parse it into something strict enough to query and chart.

That's traininglogs.

Vision

traininglogs today is a post-workout pipeline: write a markdown file, parse it, store it. The direction it is heading is a live, in-workout agent that captures sets as they happen, on mobile, by voice or tap, with the same data fidelity. Three principles guide that evolution.

Predict the row, don't capture it

Most data in a workout is predictable. The program says set 2 of bench press should be 90 kg × 8; the agent already knows that. The interaction should default to confirmation, not capture. A pre-filled row with one big tap to accept handles the majority of sets. Increment/decrement and inline edits cover small adjustments. Voice is reserved for the qualitative tax — RPE, partials, "left shoulder felt off", a drop set the program didn't predict, a new exercise added on the fly. The friction floor of an app used at 160 bpm with sweaty hands is "tap to confirm"; anything more is a cost paid for richer data, and should be optional.

The agent's job is to translate loose input into strong fields

A user can say "8 plus 2 partials at 7 RPE, felt good" without thinking about schemas. The agent's job is to turn that sentence into {reps_full: 8, reps_partial: 2, rpe: 7.0, rep_quality_assessment: "good"}. Notes are the residue — they exist for the parts of a sentence that don't map to a typed field, not as a dumping ground. This principle keeps the data model strict where it matters (queryable, chartable, comparable across sessions and users) without forcing users to learn it.

Rich primitives, loose context

The numbers you want to do math on must be numbers. The words you want to read can be words. There is no in-between. Weight, reps, RPE, duration, distance, heart rate — strongly typed and validated. Tags, modality, form cues, notes — free text. When new sports or training styles are added, the test for each candidate field is: would a user ever want to chart, filter, sum, or compare this? Yes → typed column. No → notes. Most fitness apps fail at the extremes — either everything is structured (and the model breaks on the first unfamiliar workout) or everything is loose (and nothing is queryable). The sweet spot is rich primitives plus loose context, expanded conservatively as new modalities arrive.

The shape of the system

Five things, in order:

markdown → parser (--parser rules) ──┐ files ├→ Pydantic → PostgreSQL → dashboard free-text → agent (--parser ai) ──┘ models (truth) (HTML) drafts └─ ConfirmationCard ↓ (confirm / correct) FastAPI (REST)

Each step is a boundary. Markdown is what I write. Pydantic is what the rest of the system trusts. Postgres is the source of truth for everything queryable. The API and the dashboard both read from Postgres; nothing writes back through them.

This separation means I can rewrite any one stage without disturbing the others. The Pydantic model and the database schema are the stable contract between stages — everything upstream of Pydantic can change without touching storage or the API. The rule-based parser remains available via --parser rules; the default path is the AI agent.

The data model

A session is one workout on one day. A session has three ordered groups of movements: an optional session-level warmup, the main work (exercises), and an optional session-level cooldown. Session warmup/cooldown movements are lightweight (name, reps or duration, notes) and use their own models — they are not exercises. An exercise has sets and, separately, its own optional warmup sets (e.g. ramp-up sets before a lift's working weight) — a different thing from the session-level warmup despite the shared name. A working set may carry a failure technique (myo-reps, lengthened-partials, static hold, drop set) when it's taken to RPE 10.

Fields marked = None are optional — absent means the value wasn't recorded for this session/exercise/set, not that it was zero.

A set that has both weight_kg and duration_seconds is valid — this covers timed strength work (e.g. max reps in 60s with load). There is no set_type discriminator; the fields present describe the set. Exercise classification uses free-text tags and modality rather than a fixed enum — adding a new sport or training style requires no code change.

Working sets are first-class; an exercise's own warmup sets are lower-resolution because they rarely need to be queried later. RPE is optional because it is not always logged. The model is permissive at the edges and strict in the middle — exactly the parts that get queried.

A few invariants the model enforces:

  • failure_technique is only valid on sets where rpe == 10.
  • Exercise number fields must be sequential starting at 1 — same rule for session-level warmup and cooldown movement numbers.
  • week must be between 1 and program_length_weeks (when both are set).
  • RPE is a whole or half step between 1 and 10.

Movement-skill conventions. Calisthenics, gymnastics rings, juggling, reaction drills, shadow boxing, and kettlebell/dumbbell work needed no model changes — only extraction conventions in the LLM SYSTEM_PROMPT, since the flat Set model already covers every shape involved, whether the session is ad-hoc or part of a real structured program. Skill-practice runs (juggling catches, drill attempt counts) and skill attempts (e.g. muscle-up tries) map to rep_count — for skill attempts specifically, clean completions are full and failed tries are partial, the same distinction an ordinary working set already makes (ordinary reps with varying form quality stay full — only explicit attempt/clean phrasing triggers the split). Static holds and timed rounds map to duration_seconds; measured reaction times (milliseconds) are never numeric — they go in a set's notes. Ad-hoc sessions (no program, no phase/week) leave program/phase/week all unset — no pseudo-program name is invented; these live at inputs/sessions/, mirroring the pre-existing "standalone session" concept. A session with phase/week but no stated program name also leaves program unset rather than guessing, since it belongs to a real program whose name is usually known from the file's directory path, not its text. inputs/programs/ stays reserved for real structured programs.

Remarks and unmapped text. Free-prose input often has remarks that don't map cleanly onto one field — an aside before the first exercise, an RPE stated once after a whole block of sets rather than per set. The rule: attach it as a note at the most specific level it's clearly tied to (a named set, then a named exercise or movement), and only fall back to the session-level notes field when nothing more specific applies. Nothing is silently dropped. A single RPE value stated once for a whole exercise defaults to the last set (upper bound if it's a range stated as text), flagged uncertain — never spread across every set in the exercise. An explicitly named set ("top set RPE 9") overrides the default. This replaces trying to maintain a growing dictionary of user-specific field aliases (e.g. a personal "Movement:" label): unmapped labels just fall through to the notes rule instead, since chasing every user's vocabulary doesn't scale and undermines the point of using an LLM for semantic understanding in the first place.

The parser

Markdown in, TrainingSession out. Two stages: parser/extract.py walks the markdown into an intermediate dict; parser/parse.py turns that dict into a plain dict shaped directly for Pydantic. The processor injects the session_id, runs lbs→kg conversion if needed, then calls TrainingSession.model_validate() — that's where validation fires. One model layer, no translation step.

The rule-based parser is deterministic, free to run, and has full test coverage against historical sessions. It stays available via --parser rules for debugging, offline use, and regression comparison. The default path is the AI agent described in the next section.

Storage

Two artifacts, one source of truth.

  • PostgreSQL is the source of truth. Six tables: sessions, warmups, cooldowns, exercises, working_sets, warmup_sets. warmups/cooldowns hold session-level movements (one row per SessionWarmup/SessionCooldown); warmup_sets holds an exercise's own ramp-up sets. Foreign keys cascade on delete. failure_technique is stored as JSONB with technique_type as the discriminator. No ORM; raw SQL via psycopg2. Notable columns: sessions.weight_unit, sessions.source_file (path, used by dashboard program auto-discovery), sessions.notes; exercises.tags (TEXT[]), exercises.modality (TEXT), exercises.movement_pattern (TEXT[]); working_sets.weight_kg, duration_seconds, distance_meters, heart_rate_bpm, unilateral rep columns (left_reps_full, left_reps_partial, right_reps_full, right_reps_partial). There is no set_type column — the measurement fields present on a row describe the set. data_model_version/data_model_type are not stored as DB columns — they exist only in the JSON snapshot (see Versioning below).
  • JSON snapshots are written to output_training_logs_json/ alongside the markdown, after the DB insert succeeds. They come from session.model_dump(mode="json"). Cheap, diffable, version-controllable — useful for sanity-checking the parser without touching the database.

The processor is DB-first, JSON-second: a session_id collision raises SystemExit rather than silently overwriting. Session IDs are derived from the file path (YYYY-MM-DD-sha256[:6]), so a collision means the same file was already processed.

The API

FastAPI, read-only. Three endpoints, mapped to the questions I actually ask:

EndpointAnswers
GET /sessionsWhat did I do, and when? (filterable by phase, week, date range)
GET /sessions/{id}Full detail of one session, exercises and sets included.
GET /exercises/{name}/historyHow has this lift moved over time? Every working set, every session.

Every request requires an X-Api-Key header. The app fails at startup if API_KEY is unset. Single key, no users table, no OAuth — it's mine and the dashboard's.

The dashboard

The dashboard is a single static HTML file rebuilt from the database by scripts/build_dashboard.py and written to docs/index.html. Clean white background, Inter for body text, JetBrains Mono for labels and numbers. Six sections:

OverviewTotal sessions · current plan · current phase · last session date

Strength ProgressionTop weight per day per exercise (actual kg, not e1RM); goal weight as a faded dashed red line; set-level note shown in side panel
Weekly LoadTotal kg moved per phase/week; deload weeks in red
Personal BestsHeaviest set per highlight exercise — weight, reps, date
ProgramAuto-discovered from inputs/programs/*/program.md; alias read from YAML frontmatter

The data flow at build time:

PostgreSQL → analytics/queries.py → scripts/build_dashboard.py → docs/index.html (6 SQL queries) (renders HTML + inline JSON)

The HTML embeds all data as inline JSON and renders charts with Chart.js. No server is required to view it. It is committed to docs/index.html as part of the normal traininglogs log workflow, which publishes it two ways: GitHub Pages serves this repo's own docs/ folder directly at apoorvasharma007.github.io/traininglogs; separately, the website's deploy workflow checks out this repo at build time and copies docs/index.html into the site at apoorvasharma7.com/dashboard. Neither requires an explicit push step from this repo beyond the normal commit — the website redeploy (automatic on its own pushes, or manual via workflow_dispatch) is what picks up the latest committed dashboard.

Typography and palette

Inter for body text; JetBrains Mono for labels, numbers, and monospace elements. Background #ffffff; ink #111827; accent #dc2626 (red) for emphasis, deload bars, and the current-phase hero stat; muted #6b7280 for secondary text.

Program auto-discovery

Each program lives at inputs/programs/<slug>/program.md. The file must have a YAML frontmatter block at the top with an alias field (e.g. alias: Strength & Hypertrophy). build_dashboard.py scans all matching paths at build time and renders a link for each. No code change is needed to add a new program — drop the directory and file, set the alias, rebuild.

Rules of the road

  • Never hand-edit docs/index.html — it is fully regenerated on every build.
  • Always rebuild against the real DB before judging output. Synthetic data lies.
  • e1RM (Epley formula) is intentionally absent — the chart plots actual top-set weight. Do not reintroduce it.

Versioning

Each session carries data_model_version and data_model_type fields in the JSON snapshot (not stored as DB columns — see Storage above). Schema and parser changes are tracked in CHANGELOG.md (Keep a Changelog format). The app version is stamped in the eyebrow of this document and auto-synced by CI on merge to main.

Schema changes to date have been additive (new columns with defaults). db/schema.sql is the authoritative schema; db/db.py:apply_schema() is run explicitly by migration/import scripts (not automatically on app startup). Breaking migrations will be documented here when they land.

Track B — AI capture

The default parsing path. Instead of a structured markdown format, the user writes freely — during or after the workout — and the agent maps the draft to TrainingSession. Data correctness is the top priority: nothing is written to the database until the user confirms the agent's interpretation.

The flow

free-text .md ↓ agent/llm_parser.py LLM call: free text → TrainingSession dict │ + uncertain_fields[] ↓ agent/card.py build ConfirmationCard from dict │ mark uncertain fields with ? ↓ agent/renderer.py TerminalRenderer (rich) prints card │ ↓ user: "y" or correction text │ ├── "y" → TrainingSession.model_validate() → DB write │ └── correction → agent/patcher.py → LLM patches dict ↓ re-render card → back to user prompt

TrainingSession.model_validate() always runs on the final dict regardless of path. The LLM produces input to Pydantic, never a bypass around it.

ConfirmationCard architecture

The card is a tree of dataclasses defined in agent/validation_card_data.py, built from a confirmed TrainingLogLLMExtract by agent/validation_card_builder.py. It is the stable contract between the LLM output and any renderer — terminal today, JSON/frontend later.

UserValidationCard
  SessionHeader              date · focus · duration · program / phase / week
  NotePreview = None         session-level note, shown right after the header
  SessionMovementSection[]   warmup / cooldown, each a MovementRow[]
  ExerciseCard[]
    ExerciseHeader           number · name · goal (plain English)
    WarmupRow[]               weight · reps
    WorkingSetRow[]           weight · reps · RPE · quality · failure (plain English)
    NotePreview = None        first ~40 chars of note + "…" if truncated
    NotePreview = None        same, for the exercise's own warmup notes

Fields the LLM was uncertain about are flagged in uncertain_fields: list[str] (dot-path format, e.g. "exercises[1].sets[0].weight_kg"). The renderer marks those positions with ?. The user's eyes go directly to uncertain fields; everything else can be scanned in seconds.

Form cues are not shown on the card — they are stored but low-stakes if wrong, and omitting them keeps the card skimmable. Notes (session-level and exercise-level) are shown as a truncated preview. Goals and warmup sets are shown in full because they are stored data the user should verify.

Correction loop

After the card is printed, the user sees a single consistent prompt: Confirm, or say what's wrong:. Any input other than y / yes is treated as a natural-language correction. The patcher sends the current dict and the correction to the LLM, which returns the updated dict. The card is rebuilt and re-rendered. This repeats until the user confirms.

The correction model receives the full current TrainingSession dict as context, so it can apply relative corrections ("second exercise, not the first") without the user specifying field paths.

LLM call design

CallModelInputOutput
Parseclaude-haiku-4-5raw session text + schema descriptionTrainingSession dict + uncertain_fields[]
Patchclaude-haiku-4-5current dict + user correction textupdated TrainingSession dict

Both calls use structured output (JSON mode). The schema passed to the LLM is derived from the Pydantic models — single source of truth, no duplication. Failure techniques are described in natural language in the prompt and mapped back to their structured types by the LLM.

CLI interface

# AI parser (default) — free-text input, confirmation card
traininglogs log draft.md

# Rule-based parser — structured markdown, no confirmation card
traininglogs log session.md --parser rules

All log flags (--no-commit, --pr) apply to both parser modes. The --parser flag only controls the parse stage; everything downstream is identical. Use traininglogs validate to test parsing with no DB or git side effects.
