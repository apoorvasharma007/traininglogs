traininglogs

Workout notes written however you like, turned into structured training data.

What it is

traininglogs turns workout notes written however you like into structured training data.

You paste in a session the way you'd jot it down in Apple Notes: half sentences, 100 x 3 atg, "left knee felt off on set 2". The app reads it and lays out a confirmation card showing what it understood from your note, like exercises and sets, with weights, reps and effort. You fix whatever it got wrong by tapping it, confirm, and the session lands in Postgres DB.

The goal is an app that can log any kind of training. Someone who runs, cycles, lifts and practises skills like reflex drills shouldn't need a different app, or a different format, for each. So the input stays open: no form, no template. The app's job is to make sense of what you wrote and store it reliably enough that progress can be tracked from it later.

The insights part of this application is being built: a user dashboard that turns the stored sessions into a picture of your progress.

Right now it's a personal app with a single user, running at traininglogs-875429444117.us-east1.run.app (it asks for an API key). Accounts for other people come later.

The web app

A React app in frontend/, built into static files and served by the API at /. It has five tabs: Train, Programs, Progress, History and Settings. Settings keeps your API key in the browser.

Train shows the program you follow and its next workout. Start opens a session: each exercise from the plan, with last time's weights and reps in grey. You type over them, tick each set when it's done, and add or remove sets and exercises as the day goes. Every change is saved in the browser (IndexedDB). Finish sends the ticked sets to POST /sessions once; with no connection, the session waits on the phone and sends itself when the connection returns. An exercise in a workout can list alternatives ("Shoulder Press or Bench press"); the session starts with the first, and a swap icon switches to another.

Programs holds the programs: workouts in order, back to 1 after the last. Train shows a one-line deload reminder when the followed program reaches its deload days, 28 by default.

Log from notes is the original path: paste a note, the model reads it, and Review shows the card. You type over values on the card, open a set's drawer for RPE, type and notes, or describe a change in words, which calls the model. Confirm writes the session.

Progress

The Progress tab shows six key lifts first: Squat, Bench Press, Shoulder Press, Deadlift, Barbell Clean and Pull-up, each with its latest and best estimated max, the number of sessions and an arrow for the 4-week trend. Under "Other lifts" is every other exercise trained in 3 or more sessions. Tapping a lift opens a chart with one point per session, record sessions in red and the program's goal weight as a dashed line, and below it each session's sets.

A set's estimated max is weight × (1 + (reps + reps left) / 30), where reps left is 10 minus RPE, so 1 rep at RPE 9 counts the same as 2 at RPE 10. A set without an RPE gives no estimate, since how many reps were left is unknown. Only working sets with a weight above 0, 1 to 12 full reps and an RPE of 6 or more count; a unilateral set counts its weaker side. The session's point is its best set. A session with no such set is plotted at its heaviest weight as a hollow dot, and doesn't count toward the latest, best or trend. Published RPE charts disagree with each other, which is why this uses a formula instead of a chart.

Pull-ups are mostly bodyweight, and the app stores no bodyweight, so the chart shows best reps at bodyweight with added weight on a separate axis. Which logged names count as each key lift is a fixed list in analytics/key_lifts.py (Squat and Squats, for example); stored names are never changed.

How a session flows

Every step saves before it returns, so a crash, a failed model call or a card you walk away from never loses what you wrote.

you paste a session, press Extract │ ▼ POST /inputs ├── the text, untouched → input_text └── extract() the model reads it (several calls) → ai_call_logs the assembled reading, status pending → input_text_confirmation_cards │ ▼ GET /extractions/{id} the card │ ▼ you change things (repeat as often as needed) ├── POST /extractions/{id}/edit tap to edit, add, remove no model call └── POST /extractions/{id}/correct a correction in words one model call → ai_call_logs │ ▼ POST /extractions/{id}/confirm └── confirm() the final reading, as one session → workout_sessions and its exercises, sets, warm-ups, cool-downs card marked confirmed, every change kept in its corrections

Nothing overwrites the model's reading. The app records each change, from a tap or a typed correction, as a list of {path, value} edits, appends it to the card's corrections and marks it manual or ai. So what the model read, what you changed and what the database holds stay separate for good. scripts/correction_stats.py reads that log to show which fields you correct most, and how many sets the model missed.

The page doesn't keep any state on the server between steps. Each edit or correction sends the current reading and gets the new one back, and Confirm sends the final reading with the list of changes.

A session logged in the app skips the card: POST /sessions saves it straight from its input, with no model call.

Each session has a dedup key: its date plus a short fingerprint of the text you pasted. The same text confirmed twice for the same day has the same key, and confirm refuses the second copy instead of storing a duplicate. The key is unique per person, so two people's identical notes never collide.

The AI step

The model is Claude Haiku 4.5, called through Anthropic's API. Reading one session takes several calls rather than one, so each call's answer stays short and can't hit the output limit on a long session:

CallReadsReturns
split_exercisesthe whole textthe exercises in order, each with a line that marks where it starts
extract_session_shellthe whole textdate, focus, program, phase, week, session notes, session warmup and cooldown
extract_exercise, once per exerciseonly that exercise's part of the textthe exercise with its sets and warmup sets
edit_extraction, per typed correctionthe current reading and your correctiona list of edits, never a rewritten session

Each call asks for a tool call whose schema comes from the Pydantic models, so there's no second schema to keep in sync. An answer that fails validation is sent back with the error, up to two more times. If an exercise's start line can't be found in the text, that call gets the whole text instead, with a warning on the card.

Then the checks, all plain Python:

  • Every set has to quote the line it came from, and that line has to exist in what the model was shown. The card flags any set whose source line isn't in the text.
  • Sets have to run 1, 2, 3 without gaps or repeats. A gap is what a dropped set looks like.
  • An exercise whose call fails becomes a placeholder on the card saying so, never a crash and never a silent gap.
  • The model marks fields it was unsure of. A session with no date in the text gets today's date, marked unsure, because "logged today" isn't the same as "trained today".

A typed correction comes back as edits that Python applies, so a field the correction didn't name can't change.

The app logs every call in ai_call_logs with its tokens and cost, failed calls included. Haiku 4.5 costs $1 per million input tokens and $5 per million output tokens. A session makes two calls plus one per exercise; across the first nine sessions logged in the app (September to October 2026), reading one cost between 1.5 and 4 cents.

The data

Postgres, on Supabase, is the source of truth. The design, and why, is in db-redesign-plan.md; schema.sql has every column.

Every row belongs to one person. Every table except the shared exercise list carries user_id, and each child points at its parent by (user_id, parent id), so the database itself refuses a row owned by someone other than its parent's owner, and any link to another person's row. Ids are time-ordered UUIDs (version 7) made by the code; none is built from data or chosen by the phone. Row-level security is on everywhere with no rules, so Supabase's automatic web API can't reach any row; the server connects as the tables' owner, which Postgres exempts.

TableOne row per
usersperson: their Supabase sign-in id, email, timezone, units, monthly AI limit, status and role. Private.
profilesperson's public-facing part: display name, username, picture
exercisesexercise in the shared, curated list: equipment, movement, muscles, and the other ways people write it. No owner.
user_exercisesa person's own exercise, in their words, made the first time they use a name (ignoring case and spaces), linked to a shared exercise when the name matches one
input_textwhat a session was made from, untouched: text you wrote, which the model reads; manual, a session logged in the app; or import, a session from the old markdown logs. An app session's phone id is its client_id, unique per person.

The database stores weights in kilograms; the model converts pounds as it reads. Deleting a session deletes its exercises and sets with it; deleting an input deletes its cards and call log. A person who still has data can't be deleted.

The Pydantic models

The same shape as the tables, as the code sees it. A session has an optional session-level warmup, the exercises, and an optional session-level cooldown. Session warmup and cooldown movements are their own small models, not exercises. An exercise's warmup sets are a different thing again: ramp-up sets before that lift's working weight.

Every column, with its type and rules, is in src/traininglogs/db/schema.sql, which is applied to every database the app and the tests use.

The API

FastAPI. Every endpoint except the page itself needs a Supabase sign-in pass, Authorization: Bearer <pass>, and answers 401 without a valid one. The server checks the pass's signature against Supabase's published keys, that it was issued by this environment's project for signed-in users, and that it hasn't expired; the person is the pass's account, mapped to users (a first sign-in adds them). Sign-up is closed in Supabase, so only invited people get a pass. Everything an endpoint reads or changes is that person's own: someone else's program, session or card answers 404, as if it didn't exist. The app won't start without SUPABASE_URL set.

POST /extractions/{id}/confirmWrites the session, optionally as a planned workout (program_workout_id) so the program moves on. 409 if that text was already confirmed; 422 for an unknown workout.
POST /sessionsSaves a session logged in the app, no model call and no card: its input (kind manual), then the session, with its start and end time when the phone sends them. The phone's client_id makes a repeated send return the saved session (200) instead of a second one.

Where it runs

One container, the API and the web page together, on Google Cloud Run in us-east1. It scales to zero when idle and to at most two instances under load, so it stays inside Cloud Run's free tier and traffic can't run up a bill. The database stays on Supabase, in Singapore.

PieceWhat it is
Cloud Run service traininglogs512 MiB, 0 to 2 instances, CPU only while handling a request. Runs as app-runtime.
Artifact Registry imagesThe app's images, tagged by commit. Only the newest two are kept.
Secret Managerdatabase-url, api-key, anthropic-api-key, readable by app-runtime only. Terraform creates them empty and you add the values with gcloud, so no secret is in Terraform's state. An instance that starts after you add a new version uses the new value.
Service accountsterraform applies the app layer, app-deploy ships images and works only from main, app-runtime is the running app.
GitHub sign-inWorkload identity federation. Workflows in this repository get short-lived tokens; no service account key file exists.

Infrastructure

All of it is Terraform, in infra/. Each environment is its own Google Cloud project, in two layers split by who applies them:

infra/ modules/project/ APIs, GitHub sign-in, terraform and app-deploy accounts modules/app/ Cloud Run, Artifact Registry, secrets, app-runtime environments/prod/project/ applied by hand, because it creates the pipeline's own account environments/prod/app/ applied by the pipeline

Terraform's state is in one bucket per environment, prod-traininglogs-510513-terraform-state, versioned. That bucket is the only thing created by hand. infra/README.md has the commands and the naming rules.

CI and deploys

pull request, or push to dev or main │ ▼ CI tests · terraform format and validate · plan of prod/app, posted on the pull request │ a pull request stops here ▼ push, all green deploy (deploy.yml) dev → staging, no approval · main → prod, waits for approval ├── infra terraform apply of that environment's app layer (nothing when infra/ didn't change) └── app build the image, push it, move Cloud Run onto it

Terraform owns how the service is set up; the deploy owns which image runs, so Terraform ignores the image. Staging is a practice copy in its own Google Cloud and Supabase projects. A release is merging dev into main and approving the run.

Limits and costs

  • Hosting is free inside Google's limits: Cloud Run's monthly free tier, 0.5 GB of image storage, 6 secrets. Supabase is on its free plan.
  • The model costs money: 1.5 to 4 cents to read a session, and about one call's worth per typed correction. Editing on the card and logging in the app cost nothing.
  • Invite only: people sign in by an email link from Supabase, and sign-up is closed. Supabase's built-in email allows only a few sign-in emails an hour, enough for a handful of people.
  • The app runs in the US and the database in Singapore, so every query crosses the Pacific. I haven't measured how much that slows a page down yet. An instance that has scaled to zero also takes a few seconds to start.
  • The old static dashboard (docs/index.html) is frozen: the command-line flow that rebuilt it was deleted on 2026-10-05. The user dashboard planned next replaces it.

What's next
