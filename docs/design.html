Technical Design · App v3.1.0 · 2026-10-04 · github.com/apoorvasharma007/traininglogs

traininglogs

Workout notes written however you like, turned into structured training data.

What it is

traininglogs turns workout notes written however you like into structured training data.

You paste in a session the way you'd jot it down in Apple Notes: half sentences, 100 x 3 atg, "left knee felt off on set 2". The app reads it and lays out a confirmation card showing what it understood from your note, like exercises and sets, with weights, reps and effort. You fix whatever it got wrong by tapping it, confirm, and the session lands in Postgres DB.

The goal is an app that can log any kind of training. Someone who runs, cycles, lifts and practises skills like reflex drills shouldn't need a different app, or a different format, for each. So the input stays open: no form, no template. The app's job is to make sense of what you wrote and store it reliably enough that progress can be tracked from it later.

The insights part of this application is being built: a user dashboard that turns the stored sessions into a picture of your progress.

Right now it's a personal app with a single user, running at traininglogs-875429444117.us-east1.run.app (it asks for an API key). Accounts for other people come later.

The web app

One page, served by the API itself. You paste a session into the text box and press Extract. A few seconds later the card appears: the session at the top (date, focus, program, phase, week), then each exercise with its warmup sets, working sets and notes. Values the model wasn't sure about carry an "AI inferred" flag, and anything the checks found suspicious shows in a warnings box above the exercises.

You can tap any line on the card. That opens a small form with every editable field for the line, filled in, so adding a missing RPE is as easy as fixing a wrong one. Save sends only the fields you changed. A bad value, like RPE 85 or reps the app can't read, keeps the form open with the reason underneath. The form outlines the uncertain fields, so you check those first.

Below each exercise are + Set and + Warmup set; at the bottom of the card, + Exercise. A set's form has + Set after this, for a set the model missed in the middle, and every form has Remove, which asks once more before it acts. None of this calls the model.

For a change that spans many lines ("all squat sets were 100 kg"), the text box under the card takes a correction in words. That one does call the model.

Confirm writes the session. Under the Extract button, "Or repeat a past session" lists the 15 newest sessions; picking one opens a card built from it, covered in Repeating a session.

The page keeps your API key in the browser after you paste it once, and talks to the API at its own address.

Progress

The Progress tab shows six key lifts first: Squat, Bench Press, Shoulder Press, Deadlift, Barbell Clean and Pull-up, each with its latest and best estimated max, the number of sessions and an arrow for the 4-week trend. Under "Other lifts" is every other exercise trained in 3 or more sessions. Tapping a lift opens a chart with one point per session, record sessions in red and the program's goal weight as a dashed line, and below it each session's sets.

A set's estimated max is weight × (1 + (reps + reps left) / 30), where reps left is 10 minus RPE, so 1 rep at RPE 9 counts the same as 2 at RPE 10. A set without RPE counts as taken to failure. Only working sets with a weight above 0 and 1 to 12 full reps count; a unilateral set counts its weaker side. The session's point is its best set. Published RPE charts disagree with each other, which is why this uses a formula instead of a chart.

Pull-ups are mostly bodyweight, and the app stores no bodyweight, so the chart shows best reps at bodyweight with added weight on a separate axis. Which logged names count as each key lift is a fixed list in analytics/key_lifts.py (Squat and Squats, for example); stored names are never changed.

How a session flows

Every step saves before it returns, so a crash, a failed model call or a card you walk away from never loses what you wrote.

you paste a session, press Extract │ ▼ POST /inputs ├── capture() the text, untouched → raw_inputs └── extract() the model reads it (several calls) → llm_calls the assembled reading, status pending → extractions │ ▼ GET /extractions/{id} the card │ ▼ you change things (repeat as often as needed) ├── POST /extractions/{id}/edit tap to edit, add, remove no model call └── POST /extractions/{id}/correct a correction in words one model call → llm_calls │ ▼ POST /extractions/{id}/confirm └── confirm() the final reading, as one session → sessions, exercises, working_sets, warmup_sets, warmups, cooldowns extraction marked confirmed, every change kept in extractions.corrections

Nothing overwrites the model's reading. The app records each change, from a tap or a typed correction, as a list of {path, value} edits, appends it to extractions.corrections and marks it manual or ai. So what the model read, what you changed and what the database holds stay separate for good. scripts/correction_stats.py reads that log to show which fields you correct most, and how many sets the model missed.

The page doesn't keep any state on the server between steps. Each edit or correction sends the current reading and gets the new one back, and Confirm sends the final reading with the list of changes.

A session's id is its date plus a short hash of the text you pasted. Pasting the same text twice collides on that id, and confirm refuses the second copy instead of storing a duplicate.

Repeating a session

A repeat starts from a session you've already logged, with no model call at all.

you pick a past session │ ▼ POST /sessions/{id}/repeat ├── reads the stored session ├── copies the plan: exercises, goals, cues, warmup sets, │ every set's weight and reps, program, phase, week ├── leaves out how that day went: RPE, quality, failure technique, │ rest, heart rate, duration, and every note ├── date = today, flagged for you to check → raw_inputs (kind: repeat) └── a pending extraction, model "none" → extractions │ ▼ the same card, the same edits, the same confirm as above │ └── alongside it: the source session's notes, shown read-only as "Last time" under each exercise (GET /sessions/{id})

Notes are shown, never copied: a note belongs to the day it was written, and copying it would save last week's note as today's. The page matches the "Last time" lines to exercises by name, so adding or removing sets doesn't move them.

Repeating is the start of saved programs: a week of sessions you save once and run each workout, the way Hevy does, with the card filled in and only today's numbers to change.

The AI step

The model is Claude Haiku 4.5, called through Anthropic's API. Reading one session takes several calls rather than one, so each call's answer stays short and can't hit the output limit on a long session:

CallReadsReturns
split_exercisesthe whole textthe exercises in order, each with a line that marks where it starts
extract_session_shellthe whole textdate, focus, program, phase, week, session notes, session warmup and cooldown
extract_exercise, once per exerciseonly that exercise's part of the textthe exercise with its sets and warmup sets
edit_extraction, per typed correctionthe current reading and your correctiona list of edits, never a rewritten session

Each call asks for a tool call whose schema comes from the Pydantic models, so there's no second schema to keep in sync. An answer that fails validation is sent back with the error, up to two more times. If an exercise's start line can't be found in the text, that call gets the whole text instead, with a warning on the card.

Then the checks, all plain Python:

  • Every set has to quote the line it came from, and that line has to exist in what the model was shown. The card flags any set whose source line isn't in the text.
  • Sets have to run 1, 2, 3 without gaps or repeats. A gap is what a dropped set looks like.
  • An exercise whose call fails becomes a placeholder on the card saying so, never a crash and never a silent gap.
  • The model marks fields it was unsure of. A session with no date in the text gets today's date, marked unsure, because "logged today" isn't the same as "trained today".

A typed correction comes back as edits that Python applies, so a field the correction didn't name can't change.

The app logs every call in llm_calls with its tokens and cost, failed calls included. Haiku 4.5 costs $1 per million input tokens and $5 per million output tokens. A session makes two calls plus one per exercise; across the first nine sessions logged in the app (September to October 2026), reading one cost between 1.5 and 4 cents.

The data

Postgres, on Supabase, is the source of truth. Thirteen tables: three record how a session was read, six hold the session itself, and four hold programs and pinned notes.

TableOne row per
raw_inputsthing you pasted, kept untouched; a repeat gets one too, with kind repeat
llm_callsmodel call: step, tokens, cost, time, and the last raw answer even if it failed
extractionsreading of a raw input: the model's reading, uncertain fields, warnings, status (pending, confirmed, rejected) and the list of corrections
sessionssession: date, program, phase, week, focus, duration, notes, the extraction it came from, and the planned workout it came from
warmups, cooldownssession-level warmup or cooldown movement
exercisesexercise in a session, with its goal, notes and cues
working_setsset that counts: weight, reps (full, partial, or left and right), RPE, quality, rest, duration, distance, heart rate, failure technique
warmup_setsan exercise's own ramp-up set
programsprogram: name, deload reminder in days, whether you follow it (one at a time) and since when
program_workoutsworkout in a program: its number and optional name ("Push")
program_workout_exercisesexercise in a workout's plan: warmup sets, working sets, target reps or as many as you can. No weights; a session takes them from the last time.
exercise_pinsnote pinned to an exercise name, shown in every later session of it

The database stores weights in kilograms; the model converts pounds as it reads. Deleting a session deletes its exercises and sets with it, and deleting a raw input deletes its extractions and call log.

The Pydantic models

The same shape as the tables, as the code sees it. A session has an optional session-level warmup, the exercises, and an optional session-level cooldown. Session warmup and cooldown movements are their own small models, not exercises. An exercise's warmup sets are a different thing again: ramp-up sets before that lift's working weight.

The API

FastAPI. Every endpoint except the page itself needs the X-Api-Key header, and the app won't start without API_KEY set.

EndpointDoes
GET /The web page, never cached
GET /app/The new React app, never cached. It replaces / when it's finished.
POST /inputsSaves the text, then runs the model. Returns {raw_input_id, extraction_id}; if the model fails, the app keeps the text anyway and the response says why.
GET /extractions/{id}The card for a reading, as JSON
POST /extractions/{id}/editValues changed on the card, or one line added or removed. No model call. 400 names the field when a value is invalid.
POST /extractions/{id}/correctA correction in words. One model call.
POST /extractions/{id}/confirmWrites the session, optionally as a planned workout (program_workout_id) so the program moves on. 409 if that text was already confirmed; 422 for an unknown workout.

GET /sessionsSessions, newest first, each with its exercise names. Filters: phase, week, date range, limit.

Where it runs

One container, the API and the web page together, on Google Cloud Run in us-east1. It scales to zero when idle and to at most two instances under load, so it stays inside Cloud Run's free tier and traffic can't run up a bill. The database stays on Supabase, in Singapore.

PieceWhat it is
Cloud Run service traininglogs512 MiB, 0 to 2 instances, CPU only while handling a request. Runs as app-runtime.
Artifact Registry imagesThe app's images, tagged by commit. Only the newest two are kept.
Secret Managerdatabase-url, api-key, anthropic-api-key, readable by app-runtime only. Terraform creates them empty and you add the values with gcloud, so no secret is in Terraform's state. An instance that starts after you add a new version uses the new value.
Service accountsterraform applies the app layer, app-deploy ships images and works only from main, app-runtime is the running app.
GitHub sign-inWorkload identity federation. Workflows in this repository get short-lived tokens; no service account key file exists.

Infrastructure

All of it is Terraform, in infra/. Each environment is its own Google Cloud project, in two layers split by who applies them:

infra/ modules/project/ APIs, GitHub sign-in, terraform and app-deploy accounts modules/app/ Cloud Run, Artifact Registry, secrets, app-runtime environments/prod/project/ applied by hand, because it creates the pipeline's own account environments/prod/app/ applied by the pipeline

Terraform's state is in one bucket per environment, prod-traininglogs-510513-terraform-state, versioned. That bucket is the only thing created by hand. infra/README.md has the commands and the naming rules.

CI and CD

pull request, or push to main │ ▼ CI tests · terraform format and validate · plan of prod/app, posted on the pull request │ checks only, changes nothing ▼ main, all green CD waits for approval in the GitHub environment "prod" ├── infra terraform apply of prod/app (nothing to do when infra/ didn't change) └── app build the image, push it, move Cloud Run onto it

Terraform owns how the service is set up; CD owns which image runs, so Terraform ignores the image. A release is merging dev into main and approving the run.

Limits and costs

  • Hosting is free inside Google's limits: Cloud Run's monthly free tier, 0.5 GB of image storage, 6 secrets. Supabase is on its free plan.
  • The model costs money: 1.5 to 4 cents to read a session, and about one call's worth per typed correction. Editing on the card and repeating cost nothing.
  • One user. Everyone with the API key reads and writes as that user.
  • The app runs in the US and the database in Singapore, so every query crosses the Pacific. I haven't measured how much that slows a page down yet. An instance that has scaled to zero also takes a few seconds to start.
  • Only the retired command-line flow rebuilds the old static dashboard (docs/index.html), so sessions logged in the app don't appear in it. The user dashboard planned next replaces it.

What's next
